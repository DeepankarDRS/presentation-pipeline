Nothing here is inferred from file names alone — every claim was checked by reading the source. ## 1. End-to-end request lifecycle

### 1.1 Entry points

- **CLI**: `python -m src.graph "<prompt>"` → `src/graph.py:386` `run()`. Builds `initial_state` (`src/state.py:304`), compiles the graph (`compile_graph()`, `src/graph.py:379`), calls `app.invoke(state, config)`.
- **API**: `src/api.py` (FastAPI). `POST /generate` (`api.py:341`) is the main streaming entry; it builds `initial_state` and calls `graph.stream(...)` from a background thread, translating each node's state-delta into an SSE `ProgressEvent` (`api.py:253` `_build_event`, `api.py:212` `NODE_EVENT_MAP`, `api.py:232` `_NODE_WEIGHTS`/`_estimate_progress`). Other endpoints: `POST /elicit`, `POST /plan/outline` (runs elicitor + `outline_planner_node` standalone, `api.py:659`), `PUT /plan/{run_id}/outline` (caches a user-edited outline in `_edited_outlines`, `api.py:733`/`779`), `POST /plan/outline/regenerate-slide` (`outline_replanner.regenerate_outline_slide`), `POST /plan/review` (`plan_reviewer_node` standalone), `POST /plan/refine` (re-runs `outline_planner_node` with `prior_plan`/`refine_feedback` in state), `POST /generate-from-plan` (skips all planning — slide_plans supplied directly), and the slide-edit-session family `POST /runs/{id}/edit-session`, `POST /runs/{id}/slides/{i}/edit`, `GET .../screenshot`, `GET .../xml`, `POST /runs/{id}/finalize`.
- **Runner**: `python -m src.runner` (`src/runner.py`) — batch-runs fixed test cases from `tests/cases/*.yaml` through the same `run()`/graph, for regression scoring (not traced in depth here; it is a harness around the same graph).

### 1.2 `PresentationState` (`src/state.py`)

A single `TypedDict` (`total=False`) flows through every node; each node returns only the partial dict of keys it writes (LangGraph merges them, with `Annotated[..., operator.add]` fields — `assembled_slide_plans`, `completed_slides`, `generation_history`, `slide_critic_results` — accumulating across fan-out/fan-in and per-slide loop iterations instead of overwriting). Key sub-structures (all `TypedDict`): `OutlineSlide`/`OutlinePlan` (state.py:58-73), `PlanReviewIssue`/`PlanReview` (75-88), `ComponentPlan`/`PlanFlag`/`SlidePlan`/`DeckPlan` (90-133), `AttemptRecord` (135-152, one row per LLM call: `tier`, `step`, `slide_index`, token/cost fields, `reask`), `Diagnostic`/`LayoutIssue`/`ValidateResult`/`CompileResult` (154-177), `CriticIssue`/`CriticResult`/`VisualCriticResult` (180-197), `ElicitationQuestion` (200-207). `initial_state()` (304-383) is the one constructor; it validates `theme_name` against `style_resolver.theme_names()` eagerly (raises `ValueError` at run start, not mid-run) and zero-initializes every state key.

### 1.3 Graph topology (`src/graph.py:298` `build_graph`)

Nodes registered (326 total, in registration order): `questionnaire`, `elicitor`, `elicitation_wait`, `outline_planner`, `slide_component_planner`, `slide_plan_serial`, `slide_plan_sorter`, `plan_reviewer`, `style_resolver`, `context_builder`, `generator`, `validator`, `critic`, `repairer`, `visual_repairer`, `placeholder`, `slide_router`, `deck_assembler`, `evaluator`.

**Routing functions and exactly what they branch on:**

| Function | Reads | Branches |
|---|---|---|
| `route_after_start` (74) | `slide_plans`, `test_case.components`, `outline_plan.slides`, `interactive`, `audience_context` | `slide_plans` already set OR `test_case.components` set → `"style_resolver"` (skip ALL planning). `outline_plan.slides` already set (user-edited outline, e.g. from `PUT /plan/{id}/outline`) → straight to `fan_out_slide_plans(state)` (skips elicitor + outline_planner so the edit isn't overwritten). `interactive and not audience_context` → `"questionnaire"`. Else → `"elicitor"`. |
| `route_after_elicitor` (103) | `elicitation_needed`, `elicitation_answers` | needed and no answers yet → `"elicitation_wait"` (a dead-end node that returns `{}`, i.e. the graph run ends there — the API layer is expected to resume with a fresh `initial_state(..., elicitation_answers=...)` call, there is no checkpointer wired up here). Else → `"outline_planner"`. |
| `fan_out_slide_plans` (111) | `SERIALIZE_SLIDES` (env), `outline_plan.slides` | `SERIALIZE_SLIDES` (`SLIDE_PLANNER_SERIALIZE` env, default false) → `"slide_plan_serial"`. No slides in outline → same fallback with a warning. Else → a **list of `Send("slide_component_planner", {...state, "current_outline_slide": slide})`**, one per outline slide — true LangGraph fan-out, each becomes its own node invocation receiving the full state plus that one slide injected. |
| `route_after_plan_review` (158) | `plan_review.confidence_score/approved` | Always → `"style_resolver"`. The score/approval is advisory only — logged, never gates. (`plan-reviewer-loop.md`'s "real feedback loop" with re-planning described in AGENTS.md is **not implemented**; this is still the pre-loop version.) |
| `route_after_validator` (174) | `compile_result.ok/retryable`, `retry_budget`, `retry_count`, `stall_detected`, `critic_mode` | compile failed + retryable + budget not exhausted + not stalled → `"repairer"`. compile failed otherwise → `"placeholder"`. compile ok + `critic_mode == "off"` → `_slide_done_target` (`"evaluator"` if ≤1 slide plan, else `"slide_router"`). compile ok + mode `"auto"` → `"critic"`. |
| `route_after_critic` (199) | `critic_result.passed`, `visual_repair_budget/count` | failed + budget left → `"visual_repairer"`. failed, budget exhausted → `_slide_done_target`. passed → `_slide_done_target`. |
| `route_after_visual_repairer` (215) | `visual_repair_outcome`, `visual_repair_count/budget` | `outcome == "improved"` and under budget → back to `"critic"` (re-review loop). Else → `_slide_done_target`. |
| `route_after_slide_router` (227) | `current_slide_index`, `slide_plans` | more slides left → `"context_builder"` (loops back for the next slide in the **multi-slide serial generation loop** — this is distinct from the parallel *planning* fan-out). All done → `"deck_assembler"`. |
| `route_after_repairer` (237) | — | Always → `"validator"` (repair-then-revalidate loop). |

**Edges** (326-375): `START` → (conditional) → one of `questionnaire|elicitor|style_resolver|slide_component_planner|slide_plan_serial`; `questionnaire→elicitor`; `elicitor` → (conditional) → `elicitation_wait|outline_planner`; `elicitation_wait→END`; `outline_planner` → (conditional, `fan_out_slide_plans`) → `slide_component_planner|slide_plan_serial`; `slide_component_planner→slide_plan_sorter`; `slide_plan_serial→slide_plan_sorter`; `slide_plan_sorter→plan_reviewer`; `plan_reviewer` → (conditional) → `style_resolver`; `style_resolver→context_builder→generator→validator`; `validator` → (conditional) → `repairer|critic|evaluator|slide_router|placeholder`; `critic` → (conditional) → `visual_repairer|evaluator|slide_router`; `repairer` → (conditional, always) → `validator`; `visual_repairer` → (conditional) → `critic|evaluator|slide_router`; `placeholder` → (conditional, `_slide_done_target`) → `evaluator|slide_router`; `slide_router` → (conditional) → `context_builder|deck_assembler`; `deck_assembler→evaluator→END`.

So there are **two nested loops**: (a) the compile **repair loop** `generator→validator→repairer→validator→...` bounded by `retry_budget` (default 3) and stall detection; (b) the **visual critique loop** `critic→visual_repairer→critic→...` bounded by `visual_repair_budget` (default 2); and a **per-slide outer loop** `slide_router→context_builder→generator→...→slide_router` that walks `current_slide_index` across `slide_plans` for multi-slide decks (only entered when `len(slide_plans) > 1`; `_slide_done_target`, graph.py:167, is what decides single-slide vs deck routing at every exit point).

`recursion_limit: 150` is set on every graph invocation (`run()` 425, `api.py` 328/848) — the ceiling on total LangGraph superstep transitions across all these loops combined.

### 1.4 `PresentationState` keys touched per phase

- **Planning phase** — `questionnaire_node` (`src/agents/questionnaire.py:99`) writes `audience_context`, `theme_name`, `deck_min_threshold` (CLI-interactive only). `elicitor_node` (`elicitor.py:93`) writes `elicitation_needed`, `elicitation_questions`, appends to `generation_history`. `outline_planner_node` (`outline_planner.py:86`) reads `raw_request`, `deck_settings`, `elicitation_answers`, `supplied_content`, `deck_min_threshold`, `test_case`; writes `outline_plan`, appends `generation_history`. `slide_component_planner_node` / `slide_plan_serial_node` (`slide_component_planner.py:422`/`395`) read `current_outline_slide` (fan-out) or `outline_plan.slides` (serial), `deck_settings`, `supplied_content`; write `assembled_slide_plans` (accumulator) and `generation_history`. `slide_plan_sorter_node` (`graph.py:132`) reads `assembled_slide_plans`, writes `slide_plans`, `core_hook`, `deck_plan`, `mode` ("single" vs "deck", by `len(assembled) > 1`). `plan_reviewer_node` (`plan_reviewer.py:38`) reads `slide_plans`, `outline_plan.core_hook`; writes `plan_review`.
- **Generation phase (per slide)** — `style_resolver_node` (`style_resolver.py:102`) reads `theme_name`, writes `theme_element`, `resolved_theme`. `context_builder_node` (`context_builder.py:716`) reads `slide_plans[current_slide_index]`, `resolved_theme`; writes `contract`. `generator_node` (`generator.py:95`) reads `contract`, `slide_plans`, `current_slide_index`, `raw_request`, `core_hook`, `supplied_content`; writes `current_xml`, appends `generation_history`. `validator_node` (`validator.py:35`) reads `current_xml`, `contract`, `slide_plans`, `run_id`, `retry_count`; writes `normalize_result`, `validate_result`, `compile_result`, `speaker_notes`, `layout_issues`. `critic_node` (`critic.py:122`) reads `current_xml`, `compile_result`, `slide_plans`, `critic_mode`, `theme_element`, `contract`, `layout_issues`, `visual_repair_count`, `visual_critic_result`, `pre_critic_xml`; writes `critic_result`, `visual_critic_result`, `slide_screenshots`, `pre_critic_*`, and on a failed re-review may roll back `current_xml`/`slide_plans`/`contract` to the pre-repair snapshot. `repairer_node` (`repairer.py:348`) reads/writes as documented in §2.10. `visual_repairer_node` (`visual_repairer.py:130`) similar, scoped to visual-only fixes. `placeholder_node` (`graph.py:253`) synthesizes a minimal valid slide when all repairs are exhausted.
- **Multi-slide loop** — `slide_router_node` (`deck_nodes.py:61`) reads `current_slide_index`, `normalize_result`/`current_xml`, `compile_result`, `critic_result`; appends to `completed_slides` and `slide_critic_results`, increments `current_slide_index`, and **resets every per-slide-scratch key** (`current_xml`, `normalize_result`, `validate_result`, `compile_result`, `critic_result`, `visual_critic_result`, `visual_repair_count/outcome`, `pre_critic_*`, `layout_issues`, `retry_tier`, `retry_count`, `stall_detected`) so the next slide starts clean. `deck_assembler_node` (`deck_nodes.py:155`) reads `completed_slides`, `resolved_theme`; writes `current_xml` (the combined deck XML), `compile_result`, `pptx_path`, `excluded_slides`.
- **Output** — `evaluator_node` (`evaluator.py:195`) reads nearly everything; writes `evaluation` (the full run-manifest dict, also persisted to `output/runs/{run_id}/run-manifest.json`), `pptx_path`, `passed`, and (for single-slide runs) calls `embed_deck_fonts` directly since there's no `deck_assembler` step to do it.

## 2. Agents in depth (`src/agents/*.py`)

For each: purpose, I/O schema, prompt template, model (per `models.yaml`), and how output flows downstream.

### 2.1 `outline_planner.py` / `outline_planner_schema.py`
Produces the deck skeleton: `deck_title`, `core_hook`, and one `OutlineSlide` per slide (`label`, `slide_title`, `subtitle`, `section`, `narrative_role`, `key_messages: list[str]`, `visual_emphasis`) — explicitly **not** `slide_type` or component data. `stated_slide_count()` (outline_planner.py:56) regex-parses the raw request for an explicit slide count ("6-SLIDE", "five slides", or 2+ "Slide N:" headings) and that wins over the settings-derived `deck_min_threshold`, which wins over the default of 6; `test_case.slide_count` wins over all of them. Model: `get_llm("outline_planner")` → `models.yaml` `gpt-5-mini`, `reasoning_effort: medium`, `max_tokens: 32000`. Schema forced via `.with_structured_output(OutlinePlannerOutput, method="json_schema", include_raw=True)`. After the LLM call, `clean_data()` (`src/utils/text_clean.py`) strips XML-illegal control characters the model sometimes emits, and `written_lines.brief_instructions()` / `brief_content()` / `settle_direction_lines()` (see §2.4) scrub presenter-notes/design-direction lines out of `key_messages` in place, logging a note per change. Output feeds `fan_out_slide_plans` which `Send()`s each `OutlineSlide` to `slide_component_planner`.

Prompt: `src/prompts/outline_planner/{system,user}.j2`. System prompt (full read, §3) spells out: the request is a spec (copy headlines/placeholders/number formats verbatim, never invent), the three header fields, the `core_hook` tension requirement, `key_messages`' semantic-shape → component-kind hint table, "two layers" of count (mandatory data messages vs adjustable narrative messages per `amount_of_text`), `visual_emphasis` rules (conceptual focus only, preserve user-stated ordering), slide-count/dedup rules, and caveat/"Note:" handling.

### 2.2 `outline_replanner.py`
Pure function `regenerate_outline_slide(outline_slide, core_hook, feedback, deck_settings)` — regenerates one `OutlineSlide` from user feedback during outline editing (API `POST /plan/outline/regenerate-slide`), unconditionally replacing it (no tier-gating, no merge). Uses `get_llm("outline_planner")` (same model/step config as the main outline planner) with `OutlineSlide` as the structured-output schema. Not a graph node — stateless helper called directly from `api.py`.

### 2.3 `slide_component_planner.py` (the fan-out target)
The most complex planning agent: turns one `OutlineSlide` into a full `SlidePlan` (`slide_type`, `components: list[ComponentPlan]`, `layout_hint`). Concurrency knobs (env): `SLIDE_PLANNER_MAX_PARALLEL` (default 6, semaphore — though note: the fan-out itself is pure LangGraph `Send()`, concurrency is governed by LangGraph's own executor, not an explicit semaphore visible in this file beyond the constant's declaration), `SLIDE_PLANNER_MAX_CONCURRENCY` (default 10), `SLIDE_PLANNER_SERIALIZE` (default false — forces `slide_plan_serial_node` instead of fan-out).

`planner_schema()` (line 53) reads `PLANNER_SCHEMA` env each call: `"typed"` (default) uses `PlannerSlideTyped` (per-kind component models with a real JSON object `content`, `planner_schema_typed.py`); `"string"` uses the legacy `PlannerSlide` (`planner_schema.py`, `content_data_json: str`). This is the **typed-vs-string planner schema flag** from the task brief — see §6.

Core pipeline inside `plan_single_slide()` (214): render `user.j2`/`system.j2` with `content_field` = `"content"` (typed) or `"content_data_json"` (string), `hint_capabilities.planner_capabilities_section()`, `capacity()` numbers, `node_facts.facts_text()`; call `get_llm("slide_component_planner")` (gpt-5-mini, reasoning_effort medium, max_tokens 24000) with structured output; convert the Pydantic result to a `SlidePlan` via `_planner_slide_to_state()` (122) — which for typed output calls `content_data_of()` (planner_schema_typed.py:271) to flatten the per-kind content model back into the legacy `content_data` dict shape, and for string output calls `parse_content_data()` (103, tolerant of gpt-5-mini sometimes re-nesting the field name inside the JSON string — falls back to `json.JSONDecoder().raw_decode` from the first `{`); then runs `capacity.enforce_capacity()` (component-kind rewrites when over capacity, §2.5) and computes `data_provenance` via `settings_mapper.compute_provenance()`.

**Re-ask loop**: `plan_with_reask()` (323) calls `plan_single_slide(..., finalize=False)` up to twice. After each attempt it runs `plan_checks.find_problems()` (§2.6) against the brief text; if problems exist it re-asks once with `reask_context(problems)` injected as `repair_context` in the user prompt (telling the model which component_ids failed and why). It keeps whichever of the two attempts had fewer problems (ties keep the first). If **both** attempts error outright (exception), or the kept plan `holds_no_content()` (plan_checks.py:115) while a non-empty `fallback_plan()` exists, it falls back to `fallback_plan()` (298) — a single `bullet_list` component built verbatim from the outline's own `key_messages`, tagged `plan_source: "fallback"`. This replaces an earlier version of the pipeline that silently left `components: []` and let the generator invent content. Finally `plan_checks.finalize_plan()` runs the code-owned fixes (§2.6) on whichever plan won.

`slide_component_planner_node` (422, the graph node, fan-out path) and `slide_plan_serial_node` (395, `SERIALIZE_SLIDES=true` path) both call `plan_with_reask()` per slide and append its `AttemptRecord`s to `generation_history`.

### 2.4 `written_lines.py`
Not a graph node — a library of brief-text classification helpers shared by the outline planner and the slide component planner / plan checks. Key functions: `from_brief(line, brief_text)` (70% word-overlap heuristic, `BRIEF_OVERLAP = 0.7`) decides if a line is "copied" vs "written" by the LLM; `brief_instructions(request)` (94) extracts the raw request's own presenter-notes and unlabelled design-direction sentences (regexes `NOTES_LABEL`, `_BUILD_VERB`/`_BUILD_WORDS`) so that when the outline planner rewords their label (e.g. "Speaker Notes:" → "Note:") the text is still recognized as an instruction, not content; `visual_directions()` / `drop_visual_directions()` strip "Visual:"/"Show:" design-direction lines that got copied verbatim into a component; `flag_written_lines()` marks card_grid body lines not traceable to the brief as `body_source: "written"` (surfaced to the user for Keep/Remove review via `SlidePlan.written_lines`, exposed in `api.py`'s `SlideInfoResponse.written_lines`) and strips any written line that contains a digit (numbers may never be invented); `drop_repeated_bodies()` / `drop_shared_card_lines()` remove a card body that just repeats its title, or a line/bullet identical across 3+ cards in a grid (composed-from-matrix artefacts).

### 2.5 `capacity.py`
Single source of per-kind capacity numbers, loaded from `knowledge/core/capacity.yaml` (cached, `capacity()` line 20). `span(kind, key)` renders a `[lo, hi]` range as `"lo-hi"` for prompt injection; `_jinja_env.globals` in `slide_component_planner.py:69` exposes `cap=capacity()` and `span=span` directly to the Jinja template, so the prompt's numeric limits ("3-5 items", "{{ cap.process_arrow.max_label_words }} words") are rendered from this one YAML, never hand-typed (enforced by `tests/unit/test_capacity.py`). `enforce_capacity()` (127) is a **code-only plan fixer**, run after every planner call: a `process_arrow`/`timeline` over its item cap (or with an over-long label) becomes a `card_grid` (`_to_cards`, `_as_cards`); a `flow` over capacity is only reported (flows lose their arrows if turned into cards — a deliberate 2026-10-04 decision, kept as a `capacity_fixes` note, not auto-converted); a 2-column `label | value` table of one entity whose values mix units (₹/%/x) becomes a `kpi_row` (`_metric_table_to_kpis`, 96 — the "switched visual" case, user decision L5); a `card_grid` whose `card_layout == "matrix"` but whose cells only repeat the row/column names (`_placeholder_matrix`, 117) collapses to one card per row; every `card_grid` gets `per_row` computed (`per_row()`, 68, balances rows: 7→4+3, 9→3+3+3); a `steps`-layout card grid past `steps_max` becomes a `grid`. Also hosts `layout_rules()` (181) — the generator's numeric layout guidance (hero number px range, grid gap, table column caps, split ratios), rendered into the generator's system prompt under "LAYOUT RULES".

### 2.6 `plan_checks.py`
The step-0 code-check layer (676 lines) that runs on every finalized `SlidePlan`, independent of the LLM. Two categories:

- **Problems that justify a re-ask** (`find_problems()`, 128): `PLAN_EMPTY` (no components, or every component empty via `is_empty()`, which checks kind-specific content keys in `_CONTENT_KEYS`), `PLAN_INSTRUCTION_TEXT` (a component's text is a direction to the presenter/builder, not audience content — `is_instruction_text()`, 74, uses `written_lines.NOTES_LABEL`/`_PRESENTER_VERB`/`_ADDRESSES_SLIDE`/`_PLANNER_VERB` regexes plus the brief-instruction matcher), `KPI_VALUE_TEXT` (a `kpi_row`'s `kpi_values` contains prose — `value_parts.is_sentence()`), `CARD_LINES_DROPPED` (a card got only a title though the brief gives it a line — `dropped_card_lines()`, 168, matches brief pieces starting with the card's title).
- **Code-owned fixes** (`finalize_plan()`, 652, orchestrates in order): `drop_instruction_text()` (281, also drops empty captions), `drop_repeated_bodies()`/`drop_shared_card_lines()` (written_lines.py), `drop_duplicate_items()` (`PLAN_DUPLICATE_ITEMS`, 254 — two list-like components whose item labels overlap ≥70% are collapsed, keeping the heavier one by text mass/weight), `drop_repeated_layers()` (`LAYER_REPEATED`, 336 — a free-hand `layer` component is dropped if another visual already shows its words, or if it only names a visual with no items of its own, unless it's the slide's only visual), `cards_to_list()` (`CARDS_TO_LIST`, rule "K4", 451 — a ≥6-card grid of mostly-short cards on an already-dense slide (≥80 words elsewhere) becomes a `bullet_list`), then per-component `settle_kpi_tones()` / `settle_kpi_icons()` / `settle_card_fields()` (559-648 — validate/clean `kpi_tones`, `kpi_icons`, card `tone`/`key_phrase`/`icon`/`focus_card` against real icon names and derive tones from the `design_hint` text via `tones_from_hint()` when the planner wrote none), and finally `sparse_flag()` (`SLIDE_SPARSE`, 407 — report-only "thin slide" heuristic based on a rough per-kind "unit" weight, `SPARSE_UNITS = 9`).

All findings land in `SlidePlan.plan_flags` (`{code, component_id, detail}`) and a human-readable note is appended to `SlidePlan.capacity_fixes` for every change — this is the trail visible in eval bundles explaining "why" a plan was altered.

### 2.7 `context_builder.py` (`context_builder_node`, 716)
No LLM. Builds the **generation contract** for one slide from its `SlidePlan` + resolved theme: `build_contract()` (558) selects the POM node vocabulary needed for this slide's component kinds (`_select_nodes`/`_KIND_TO_NODES`, `_select_attributes`, `_build_node_hierarchy` — from `knowledge/core/nodes.yaml`), forbidden tags/attrs (`knowledge/core/validation.yaml`), theme element/colors, component-specific notes (`_select_notes`, 265 — pulls `pitfalls`/`facts`/`structure` from each `knowledge/components/<kind>.yaml`, plus `core/design-language.yaml`'s `content_rules`/`design_principles`/`card_recipe`/`bullet_list_styling`/`chart_sizing`/`table_styling`), the house-style grammar text (`_render_house_style()`, cached, renders `knowledge/core/house-style.yaml` section-by-section) plus `capacity.layout_rules()`, concrete **component recipes** (`_render_component_recipes()`, from `knowledge/core/recipes.yaml`, keyed per kind/layout via `_KIND_TO_RECIPE`/`_recipe_kind()`), golden XML examples (`_render_golden_examples()`, only when `POM_EXAMPLES=on`, env `EXAMPLES_ON`, line 555 — default off since 2026-10-08), a selected **blueprint** (`blueprint_selector.select_blueprint()`, deterministic scoring, no LLM — §2.19), **visual-intent technique** text and per-component **hint scopes** (`hint_capabilities.py`, §4), and the curated icon vocabulary (`knowledge/components/icon.yaml`).

Crucially, when `tiles.on()` is true (`POM_BLOCKS=tiles`), `build_contract()` **removes** the `kpi_row`/`hero_stat`/`card_grid`/`card_steps` recipes and hand-built visual-intent techniques for components that will instead be drawn by the tile/card node expansion (`cards.card_components()`), replacing their "scope" line with the tile/card module's own `scope()` (which reports only the subset of planner-asked treatments that the tile/card attribute vocabulary can actually draw). This is the mechanism by which `POM_BLOCKS` changes what the generator is told to write, not just what the compiler does after the fact.

`context_builder_node` also has a `_build_default_plan()` fallback (685) used only when `slide_plans` is entirely empty (test-case/intent-detection/`title+narrative+bullet_list` fallback chain) — this is the "skip-planner" path's safety net, not used when the planner ran.

### 2.8 `generator.py` (`generator_node`, 95)
No structured output — raw text completion expected to be bare POM XML. `_render_prompts()` (30) renders `src/prompts/generator/{system,user}.j2` from the `contract` dict and the current slide's `SlidePlan`. Notably: when `element_refs.refs_on()` (`POM_BLOCKS` is `kpi` or `tiles`), every `kpi_row` component with a `component_id` has its `content_data` **blanked out** in the user prompt and replaced by a `ref_line` (either `tiles.prompt_line` or `element_refs.prompt_line` depending on `tiles.on()`) — i.e. **the generator is never shown the actual KPI numbers**; it only sees shape/length metadata and must place `<Text ref="...">` placeholders. Under `tiles.on()` the same blanking happens for `card_grid` components that `cards.card_components()` claims to draw (all cards, since matrix layout is deferred). `tiles.on()` also appends `tiles.node_lines() + cards.node_lines()` as `tile_nodes` in the system prompt (the fixed `<KpiGrid>/<Kpi>` and `<CardGrid>/<Card>` tag-vocabulary block). Model: `get_llm("generator")` → gpt-4.1, temperature 0.2, max_tokens 12000. Truncation (`finish_reason == "length"`) is recorded on the `AttemptRecord` (used by the repairer's strategy chooser). On any exception the node fails soft, returning `{"current_xml": ""}` (validator then reports `EMPTY` and the repair loop fires).

### 2.9 `validator.py` (`validator_node`, 35) — mechanical, no LLM
The ground truth for retry decisions. Pipeline, in order:
1. If `element_refs.refs_on()`: fix a bare `&` (`_BARE_AMP_RE`), then call `tiles.fill(xml, plan)` or `element_refs.fill_refs(xml, plan)` (depending on `tiles.on()`) — this is where `<KpiGrid>/<Kpi>`/`<CardGrid>/<Card>` tags get expanded and every `<Text ref="...">` gets its literal text written in by code (§5.4). If this step reports any `severity: "error"` issue, the validator **returns immediately** with a synthetic `compile_result.ok=False, retryable=True` — the repair loop fires without ever reaching `normalize_xml`/the Node compiler.
2. `normalize_xml(xml)` (`normalizer.py`, §5.2) — the big deterministic-fix pass; its `issues` are prepended with the ref-fill issues (marked `auto_fixed` = severity != "error").
3. Dark-panel de-duplication across slides of a deck (`has_dark_panel`/`soften_dark_panels` — "one dark panel per deck" house rule).
4. `ensure_single_theme()` injects the canonical `<Theme>` element.
5. `content_model.nesting_compile_failure()` — if normalize found any `INVALID_CHILD` violation, return a failure immediately (skips the Node compiler entirely: POM's own error message for bad nesting is either misleading, for `<Td>`, or silently-absent, for `<Li>`, so this check must run first).
6. `compiler_client.validate_xml()` (parseXml-only, fast) — on `None` (compiler unreachable) falls back to a Python regex pre-validator `pre_validate()`; on structural failure, return immediately.
7. `compiler_client.compile_xml()` (full buildPptx via Node subprocess) — wrapped in `CompilerError` handling (non-retryable `HARNESS_ERROR`).
8. `layout_audit.audit_layout()` (mechanical XML checks) plus, only on a successful compile, `geometry_audit.audit_run_folder()` (compares POM's own positioned-box JSON against what actually got drawn into the `.pptx`).

Returns `normalize_result`, `validate_result`, `compile_result`, `speaker_notes` (extracted from a stripped `<Notes>` element), `layout_issues`. `normalize_and_compile()` (207) is a smaller variant reused by the visual repairer and slide-edit service to re-check a candidate XML without going through the full node.

### 2.10 `repairer.py` (`repairer_node`, 348)
Two strategies, `PATCH = 1` / `REGENERATE = 2` (constants, 65). `_choose_strategy()` (248): attempt 1 is always `PATCH` **unless** the visual critic already flagged `layout_broken`/`visual_only_failure`, in which case it's `REGENERATE` immediately. After attempt 1: if the previous strategy was `REGENERATE`, the next is a `PATCH` "cleanup" pass. Else, `REGENERATE` is forced by: the previous `PATCH` being a no-op or truncated, a structural error (`needs_regeneration()` — `INVALID_CHILD` or "unexpected child"/"child elements" text in a diagnostic), a detected stall (`is_stalled()` — ≥65% of current error signatures match the previous attempt's), a visual-only failure, or simply reaching attempt ≥2 while still not compiling. So the designed loop shape is **PATCH → REGENERATE → PATCH (cleanup)**, capped by `retry_budget` (default 3).

`PATCH` (`build_patch_prompts()`, 200, shared with `slide_edit_service.py`) sends the failing XML + capped/deduped error list + `repair_guidance.build_error_guidance()` (targeted fix text per error code) + `repair_guidance.select_repair_knowledge()` (loads only the `knowledge/components/<Node>.yaml` slices for nodes actually named in the errors) to `get_llm("repairer")` (gpt-4.1, max_tokens 12000). When `visual_only=True` (no compile errors, only visual-critic issues), the design context (`house_style`/`component_recipes`) is injected and the instruction shifts from "fix only errors" to "apply visual improvements, no new panels/boxes" — this is also where the critic's own instruction *not* to re-invent card-in-card wrappers lives.

`REGENERATE` (460-616) re-plans the single slide via `slide_component_planner.plan_single_slide()` with a `repair_context` built by `_build_repair_context()` (123 — picks `_RELIABLE_COMPONENTS`/`_RISKY_COMPONENTS` to recommend/avoid based on which kinds were on the failing slide), rebuilds the contract via `context_builder.build_contract()`, and calls `get_llm("generator")` fresh — i.e. a REGENERATE attempt is actually **two LLM calls** (re-plan + re-generate), both logged as separate `generation_history` entries (the re-plan's usage is recorded under `step="slide_component_planner"`). Any exception anywhere in the REGENERATE path falls back to a `PATCH` using the pre-REGENERATE state. `route_after_repairer` always sends back to `validator`.

### 2.11 `critic.py` (`critic_node`, 122) + `visual_critic.py` (`run_visual_critic`, 64)
`critic_node` is the orchestrator: on first entry (`visual_repair_count == 0`) it snapshots `pre_critic_xml`/`pre_critic_slide_plans`/`pre_critic_contract`/`pre_critic_score` (`compute_critic_score()`, 37 — `-10`/`-3`/`-1` per high/medium/low issue plus an assessment penalty) before anything else. `_run_visual_review()` (69) renders a screenshot of the already-compiled `.pptx` via `compiler.screenshot.render_screenshots()` (PowerPoint COM automation, Windows-only, §5.7) — reading the *fitted* XML (`fitted.xml`, written by fit-grow) rather than the pre-fit `current_xml`, since sizes change post-generation — and calls `visual_critic.run_visual_critic()`. The result's issues are filtered through `code_owned()` (`visual_critic.py:59`) which drops any issue whose text is about font-size/padding/gap/grow/empty-space/oversizing **and not** also about a visible defect (overlap/clipping/contrast) — because those are owned by fit-grow and re-applied after every repair, so an LLM "fix" there would just be undone or fight the code pass. `passed = not (has_high or has_medium)` — low-severity issues never fail the gate. On a **re-review** (`visual_repair_count > 0`) that still fails, if the new `compute_critic_score()` is not strictly better than `pre_critic_score`, the node **rolls back** `current_xml`/`slide_plans`/`contract` to the pre-repair snapshot and force-marks the slide as passed — i.e. a repair that doesn't measurably improve the score is discarded rather than shipped.

`run_visual_critic()` builds a vision-model message (`src/prompts/visual_critic/{system,user}.j2`, base64 PNG + XML + plan + theme + compile/layout warnings + previous-round issues on a re-review) and calls `get_llm("visual_critic")` (gpt-4.1, max_tokens 800) with `.with_structured_output(VisualCriticOutput, ...)`. **See §8.1 for a likely latent bug**: `VisualCriticOutput` (in `critic_schema.py`) uses bare `Literal[...]` annotations without importing `typing.Literal`, and the module has `from __future__ import annotations`.

### 2.12 `visual_repairer.py` (`visual_repairer_node`, 130)
One-shot (per round) repair strictly for visual-critic issues, kept separate from the compile-repair loop so visual fixes never re-enter it. Honors `repair_hints.strategy` from the critic ("patch" → `_do_patch`, one LLM call reusing `repairer.build_patch_prompts(..., visual_only=True)`; "regenerate" → `_do_regenerate`, re-plan + re-generate like the compile repairer's REGENERATE). After the LLM call, it **re-compiles** the candidate via `validator.normalize_and_compile()`; if that fails, the repair is discarded (`visual_repair_outcome: "error"`) and the previously-compiled XML is kept untouched in state. If it compiles, `visual_repair_outcome: "improved"` and the new `compile_result`/`current_xml` (and, for REGENERATE, `slide_plans`/`contract`) are written — `route_after_visual_repairer` then sends back to `critic` for the re-review that will decide (via the score comparison in §2.11) whether to actually keep it.

### 2.13 `deck_nodes.py` — `slide_router_node` / `deck_assembler_node` (only active when `len(slide_plans) > 1`)
`slide_router_node` (61) persists the **normalized** XML (not the raw LLM output — auto-fixes must survive into the deck compile) plus the critic verdict into the accumulators, advances `current_slide_index`, and resets all per-slide scratch state (listed in §1.4). `deck_assembler_node` (155) sorts `completed_slides`, drops any with `compile_ok=False` (`excluded_slides`), calls `assemble_deck_xml()` (31 — extracts each `<Slide>` block via regex, strips per-slide `<Theme>`s, concatenates under one canonical theme, re-runs `normalize_xml`+`ensure_single_theme` on the combined doc so no per-slide auto-fix is lost), then `compiler_client.compile_xml()` on the whole deck. If the **combined** compile fails, `_zip_merge_fallback()` (120) stitches the individual already-compiled per-slide `.pptx` files together at the OPC/ZIP level (`compiler.pptx_merge.merge_pptx_files`) — a belt-and-suspenders guarantee that a deck is always produced even if the re-combined XML somehow fails to compile as one document. On final success, `font_embed.embed_deck_fonts()` runs once on the assembled file.

### 2.14 `evaluator.py` (`evaluator_node`, 195) — mechanical, no LLM
Computes `passed = compile_ok and critic_ok and slides_complete`; aggregates token/cost totals per `AttemptRecord` via `_compute_cost()` (35, uses `llm_client.get_pricing()` and bills cached input tokens at the model's `cached_input` rate); builds `_run_provenance()` (git commit/dirty flag/request hash) and the full `run-manifest.json` (written to `output/runs/{run_id}/`); generates **final** screenshots by re-rendering the fully-assembled `.pptx` fresh (`_generate_final_screenshots()`, 146 — deliberately not reusing per-slide critic screenshots, which for a multi-slide deck would all collide on the filename `slide-0.png` since each was rendered from its own standalone single-page `.pptx`); and writes `slides.json` (`_write_slides_data()`, 99 — the per-slide XML + plan + screenshot-path record consumed by the slide-edit-session API).

### 2.15 `elicitor.py` / `elicitor_schema.py`
`check_and_elicit()` (36) is a reusable pure function (not state-coupled) wrapping an LLM call with `ElicitorOutput` structured output (`is_sufficient`, `reasoning`, up to 5 `ElicitationQuestion`s). `elicitor_node` (93) is the graph wrapper: a no-op if `elicitation_answers` already present; otherwise calls `check_and_elicit()` and writes `elicitation_needed`/`elicitation_questions`. Model: `get_llm("elicitor")` → gpt-4.1, max_tokens 1000, temperature 0.2.

### 2.16 `questionnaire.py` (`questionnaire_node`, 99)
CLI-only interactive flow (`input()` prompts) — audience, data density, theme (dynamically listed from `knowledge/theme/palettes.yaml`), slide count, focus. No LLM. Writes `audience_context`, `theme_name`, `deck_min_threshold`. Entirely skipped unless `interactive=True` and no `audience_context` is already supplied.

### 2.17 `style_resolver.py`
`resolve_theme(theme_name)` (86) is the pure, reusable theme resolver — `_build_theme()` (49) merges a `palettes.yaml` entry's authored tokens with **derived** tokens from `compiler.palette_tokens.derive_tokens()` (§5.6) and computes `chart_colors_json`/`chart_focus` (literal-hex pair for a focused chart series, since `$tokens` can't be used inside `chartColors`). `DEFAULT_THEME` (78) is built once from the `corporate-slate` YAML entry itself (not hardcoded) so it can never drift from the palette file. `theme_names()` is what `api.py`'s `_known_theme` validator and `initial_state`'s eager check both call. `style_resolver_node` (102) is the thin graph wrapper writing `theme_element`/`resolved_theme`.

### 2.18 `settings_mapper.py`
`DeckSettings` (pydantic model, 20) is the Gamma-style pre-generation form schema (`text_mode`, `amount_of_text`, `write_for`, `tone`, `theme`, `user_prompt`, `additional_instructions`, `slide_count`). `settings_to_constraints()` (108) maps it to the flat constraint dict injected into planner prompts (`provenance_rule`, `content_level`, `narrative_guidance`, `deck_min_threshold` via `SLIDE_COUNT_TO_THRESHOLD`). `compute_provenance()` (123) tags each `content_data` key `"user"` vs `"sample"` by checking membership in `supplied_content` — feeds the evaluator's `data_provenance` counts.

### 2.19 `blueprint_selector.py`
Deterministic (no LLM) scorer (`_score_blueprint()`, 32) matching a `SlidePlan` against `knowledge/core/blueprints.yaml` entries by `slide_type`, required/any/excluded component-kind sets, density, and chart count. Returns the best-scoring blueprint dict (`structure` rendered into `blueprint_structure` text + optionally `reference_xml`, only when `POM_EXAMPLES=on`) if its score ≥ 10.0, else `None` (→ generator falls back to the grammar-only / golden-example path).

### 2.20 `hint_capabilities.py`
Renders `knowledge/core/hint-capabilities.yaml` for both sides of the `design_hint` contract: `planner_capabilities_section()` (36, into the planner's system prompt — which treatments each kind supports, and what it must `never` get), `visual_intent_techniques(kinds)` (50, into the generator's system prompt — the concrete POM-attribute technique for each treatment this slide's kinds support), `hint_scopes(kinds)` (60, one short "treatments: a, b, c. never: ..." line per component in the generator's user prompt). This is the single source enforcing the "core nodes keep fixed syntax, enrichment is composed around them" composition rule.

### 2.21 `planner_schema.py` / `planner_schema_typed.py`
Covered functionally in §2.3; structurally: `planner_schema.py` defines `PlannerComponent`/`PlannerSlide` with a single freeform `content_data_json: str` field whose docstring enumerates the JSON shape per kind (the "string" schema). `planner_schema_typed.py` defines one `_Strict` (pydantic, `extra="forbid"`) content model per kind (`TitleContent`, `KpiRowContent`, `ChartContent`, `CardGridContent`, `LayerContent`, etc., 35-189) and dynamically builds one component model per kind via `create_model()` (218-225, `COMPONENT_BY_KIND`), unioned into `TypedComponent`. `PlannerSlideTyped.model_json_schema()` is overridden (251) to strip `title`/`default` keywords via `_trim()` (230) — cutting the schema size sent to OpenAI by roughly a third, since strict mode makes every field required anyway. `content_data_of()` (271) / `content_from_data()` (281) are the adapters back and forth to the legacy flat dict shape used everywhere else in the pipeline (plan checks, generator, tile nodes, repairer).

### 2.22 `slide_edit_service.py` / `slide_replanner.py`
Post-generation "slide editor" API support (`POST /runs/{id}/slides/{i}/edit`), not part of the main graph. `slide_replanner.resolve_slide_plan()` (57) decides whether the existing `SlidePlan` already covers the user's NL feedback (cheap keyword detection via `context_builder._detect_components_from_text()`); if the feedback introduces a component kind the plan never had, it calls `slide_component_planner.plan_single_slide()` to re-plan just that slide, merging content_data so already-confirmed values are never silently overwritten (`_merge_content_data()`, 27 — original values always win over the replan's fresh guess). **See §8.2**: this call site does not unpack the `(SlidePlan, usage)` tuple `plan_single_slide()` returns. `slide_edit_service.edit_slide_xml()` (128) is the actual LLM-powered XML editor: one `get_llm("slide_editor")` call to apply the feedback, then a bounded (`MAX_REPAIR_ATTEMPTS = 2`) mini repair loop reusing `repairer.build_patch_prompts()`, then an optional single-round visual-critic + visual-repair pass (`_run_visual_check_loop()`, 251, `max_visual_repairs` default 1).

## 3. Prompts (`src/prompts/*/`)

Each subfolder is a Jinja2 `FileSystemLoader` environment owned by its agent module. Dynamic context is injected exactly as enumerated in §2's "reads" per agent; here are the structural notes and representative excerpts not already quoted above.

- **`outline_planner/`** (`system.j2` fully quoted/summarized in §2.1; `user.j2` renders `raw_request`, `deck_settings`, `constraints`, `elicitation_answers`, `supplied_content`, `target_slides`, `slide_count_source`).
- **`outline_replanner/`** — small system/user pair; `user.j2` renders the single `outline_slide` dict, `core_hook`, `feedback`, `deck_settings`; reuses the same `OutlineSlide` schema as the main planner.
- **`slide_component_planner/`** — `system.j2` (quoted at length in §1's sibling read) is the largest prompt in the repo: the semantic-routing table (key_message shape → component kind), the "decision priority" disambiguation rules (table vs kpi_row vs matrix vs card_grid), the full component vocabulary with capacity numbers interpolated via `{{ cap.* }}`/`{{ span(...) }}`/`{{ facts(...) }}` Jinja calls (so it is impossible for the prompt text to drift from `capacity.yaml` / `knowledge/components/*.yaml` `facts`), weight-assignment rules, the `design_hint` contract (rendered from `{{ hint_capabilities }}` = `hint_capabilities.planner_capabilities_section()`), and five full worked input→output JSON examples disambiguating the most-confused routing decisions (one entity's metrics → kpi_row not a 2-col table; one measure across entities → sorted chart not kpi_row; entities×measures → table; grouped items → one card per group; parallel items with lines → card_grid). `user.j2` renders the single outline slide, `core_hook`, `deck_context` (every slide's title, for cross-slide awareness), `constraints`, `supplied_content_for_slide`, and — on a re-ask — `repair_context` (`failed_kinds`/`errors`/`directive` from `plan_checks.reask_context()`).
- **`plan_reviewer/`** — `system.j2` (quoted in full above) defines the 5 review dimensions and the 5-band confidence-score rubric and the 5 issue types. `user.j2` renders every `slide_plans` entry plus `core_hook`.
- **`generator/`** — `system.j2` (quoted in full in §1) and `user.j2`; plus `nodes_rules.j2` (included only `{% if nodes %}`, i.e. only on the inactive node-contract path, §5.8) and `nodes_user.j2` (the node-arm's user template, rendered by `compiler.nodes.prompt_lines.render_prompts()`, also inactive in the live graph). The system prompt is explicitly structured with a cache-friendly boundary comment (`## THIS SLIDE`): everything above is deck-invariant (static rules → theme → narrative anchor → `deck_notes`), everything below is per-slide, so an OpenAI-side prompt cache can serve the shared prefix across every slide of a deck — this is tested by `tests/unit/test_generator_cache_order.py` per the inline comment at line ~73.
- **`repairer/`** — `system.j2` (quoted) + `patch.j2` (the PATCH user prompt: previous XML + numbered error list + `guidance` + a `visual_only` branch in the instructions).
- **`visual_critic/`** — `system.j2` (quoted in full) is the 10-item checklist plus the explicit "CODE-OWNED" section telling the vision model never to raise or patch sizing/spacing issues (fit-grow owns them) and never to invent a source/kicker that the plan doesn't name. `user.j2` injects the base64 screenshot as an `image_url` content block alongside the XML, plan, theme, compile/layout warnings, and (on a re-review) the previous round's issues with an instruction to only report new or still-unfixed ones.
- **`elicitor/`** — `system.j2` (quoted) + `user.j2` (renders `raw_request`, `additional_instructions`, `deck_settings`, `supplied_content`, `domain_hint`).
- **`slide_editor/`** — system/user pair for the post-generation NL-edit flow (`slide_edit_service.py`); system prompt built from the slide's existing `contract` (`forbidden_tags/attributes`, `allowed_nodes`, `notes`, `house_style`), user prompt carries `current_xml`, `theme_element`, `feedback`, plan context.
- **`storyline/` / `slide_designer/`** — belong to the **inactive** `src/planning/` Test-1 path (`src/planning/graph.py`), not reachable from `src/graph.py`. Not traced further here; see AGENTS.md's own notes that this path was evaluated and *not* taken to production (kept for code reuse, e.g. `src/planning/checks.py`, `brief_index.py`).

## 4. Knowledge files (`src/knowledge/`)

### 4.1 `core/`
- **`nodes.yaml`** (309 lines) — the content model: per-section (`structural`, `layout`, `content`, `phase_b/c/d`, `post_mvp`, `inline`, plus `tile_nodes`/`deferred` markers) node definitions with `children` (allowed child tags, or `none`, or an "any" sentinel) and `node_attributes`. This is the **single source** consumed by `compiler.content_model.content_model()` (parent→allowed-children map, used for the blocking `INVALID_CHILD` check and the text-container-flattening safe-list) and by `context_builder._build_node_hierarchy()`/`_select_attributes()` (which nodes/attributes to show the generator for this slide's kinds). Also defines the historical phase allowlists (`phase_a_allowlist` … `post_mvp_allowlist`) — vestigial from an earlier phased-rollout design; current code loads the full node set regardless of phase, keyed only by component kind.
- **`capacity.yaml`** — per-kind item/row/column caps and the `layout` block (hero-number px range, grid gaps, table column/row px, split ratios). Read by `agents/capacity.py`; enforced by `agents/plan_checks.py`/`agents/capacity.py:enforce_capacity`; rendered into the planner prompt via Jinja globals; cross-checked against prose by `tests/unit/test_capacity.py`.
- **`hint-capabilities.yaml`** — the `design_hint`/visual-intent contract (§2.20): `treatments` (intent + POM technique per treatment id) and `kinds` (which treatments each component kind may use, plus a `never` list). Consumed by both `agents/hint_capabilities.py` (planner + generator prompt rendering) and implicitly enforced by the generator's instructions never to nest enrichment inside a core node.
- **`house-style.yaml`** (288 lines, sections: `frame`, `vocabulary`, `alignment`, `composition`, `header_band`, `sizing`, `data_nodes`, `recipes`, `type_ramp`, `font_floor`, `spacing_scale`, `color_discipline`, `color_roles`, `render_gotchas`, `design_variety`, `checklist`) — the compositional grammar text injected verbatim (via `context_builder._render_house_style()`) as the generator's "LAYOUT GRAMMAR" section. Teaches band composition, weight→grow mapping, data-node sizing rules (Chart/Table/Matrix/ProcessArrow/Flow/Pyramid/Tree/Timeline), the fixed font-size ramp, the 2/4/6/8/.../22 spacing scale, and the fixed colour-role meanings (same on every slide).
- **`recipes.yaml`** (478 lines, one entry per recipe id: `kpi_row`, `chart_card`, `table_card`, `bullet_list`, `icon_bullet_list`, `badge`, `callout`, `timeline`, `matrix`, `process_arrow`, `flow`, `pyramid`, `pyramid_with_annotations`, `layer_diagram`, `tree`, `compact_kpi_strip`, `dark_callout_panel`, `card_grid`, `card_steps`, `card_matrix`, `hero_stat`) — copy-the-shape XML snippets injected per the slide's component kinds via `context_builder._render_component_recipes()`/`_KIND_TO_RECIPE`/`_recipe_kind()`. These are **suppressed** for `kpi_row`/`card_grid`/`card_steps` when the corresponding tile/card node route is drawing that component in code (§2.7, §5.4).
- **`block-variants.yaml`** (509 lines) — the "node contract" tag/variant vocabulary for **two** experimental systems: (a) the inactive native/derived `blocks:` section read by `compiler/nodes/spec.py` for the never-wired-up 1a node route (§5.8); (b) the **active** `tile_nodes:` section (kpi + card) read by `compiler/nodes/tiles.py`/`cards.py` under `POM_BLOCKS=tiles` — house looks, variants (with `requires`/`fallback`/`with_color`/`with_tone` chains), part-attribute vocabularies, treatments. This file is the data half of §5.4/§5.5.
- **`validation.yaml`** — `forbidden_tags`/`forbidden_attributes` (HTML/CSS leakage blocklist) and `semantic_rules`/`translations` consumed by `context_builder._select_notes()` and the regex `pre_validate()` fallback in `normalizer.py`.
- **`blueprints.yaml`** (839 lines) — named layout skeletons (`match` criteria + `structure.bands`/`reference_xml`) scored by `agents/blueprint_selector.py`.
- **`golden-examples.yaml`** — full polished XML examples keyed by slide-type bucket (`data`/`narrative`/`cover`), surfaced only when `POM_EXAMPLES=on`.
- **`design-language.yaml`** — `content_rules` (always included), `design_principles`/`card_recipe.rules`/`bullet_list_styling`/`chart_sizing`/`table_styling` (included only when the slide has no blueprint-grammar coverage — in practice `has_grammar` is always `True` in the current `build_contract()`, so these extra sections are effectively always skipped except `content_rules`; see §8.3).
- **`attributes.yaml`** — common box-model attribute reference used by `repair_guidance.select_repair_knowledge()`'s layout-overflow fallback.
- **`icon-names.txt`** — the flat allow-list of valid Lucide icon slugs, exported from the installed compiler by `scripts/export_icon_names.py`; the single source for `compiler/icons.py:valid_icon_names()`.

### 4.2 `components/*.yaml` (chart, drawing, flow, icon, list, matrix, process-arrow, pyramid, shape, table, text, timeline, tree)
Each is consumed from three directions: (1) `context_builder._select_notes()` pulls `structure`/`pitfalls`/`facts` (generator-audience) into the generation contract; (2) `repair_guidance.select_repair_knowledge()` pulls `attributes`/`pitfalls`/`facts`/`notes`/`structure` into the targeted repair prompt, keyed by which POM node actually appeared in an error; (3) for the six diagram kinds (`flow`, `process-arrow`, `timeline`, `tree`, `matrix`, `pyramid`), `compiler/node_facts.py` reads each file's `facts:` list (tagged `syntax`/`layout`/`capacity`/`advice`, and `for: [planner|generator]`) plus `open_choices` and `refuted` — every `syntax`/`layout` fact is backed by a tiny compiled probe slide in `src/node/probe-facts.js` with Python-side assertions (`tests/unit/test_node_facts.py`), so a wrong claim about what POM actually draws fails a unit test instead of silently drifting into prompts. `icon.yaml`'s `recommended_names` feeds `context_builder._render_icon_names()`.

### 4.3 `theme/palettes.yaml`
Authored palette entries (10-12 tokens each: `surface`, `surfaceAlt`, `accent`, `accentAlt`, `positive`, `negative`, `warning`, `textMain`, `textMuted`, `border`, optionally `chartSurface`/`chartInk`/`chartColors`/`neutral`/`panelDark`/`onPanelDark`). Read only by `agents/style_resolver.py` (`_palettes()`); `compiler/palette_tokens.derive_tokens()` computes everything else (§5.6).

### 4.4 `examples/*.xml`
Standalone reference POM documents (`chart-slide.xml`, `drawing-slide.xml`, `flow-slide.xml`, `inline-formatting-slide.xml`, `kpi-slide.xml`, `minimal-slide.xml`, `mixed-slide.xml`, `table-slide.xml`, `text-slide.xml`, `timeline-slide.xml`) used by `tests/unit/test_upstream_reference.py`/offline-render tooling, not injected into any live prompt path directly (distinct from `core/golden-examples.yaml`, which is the one actually Jinja-rendered into the generator prompt).

## 5. Compiler bridge in depth

### 5.1 The full pipeline, in exact order, for one slide's XML

```
generator LLM text
  │
  ▼ (validator.py)
[if POM_BLOCKS in {kpi,tiles}] fix bare '&' → tiles.fill() / element_refs.fill_refs()
  │   (tiles.fill = cards.expand → tiles.expand → element_refs.fill_refs)
  │   any severity="error" issue → FAIL immediately (repair loop), skip the rest
  ▼
normalizer.normalize_xml()              (huge deterministic-fix pass, §5.2)
  │   dark-panel de-dup across the deck → ensure_single_theme()
  ▼
content_model.nesting_compile_failure() → FAIL immediately if any INVALID_CHILD
  ▼
compiler_client.validate_xml()          (Node: parseXml only — fast structural check)
  │   None (Node unreachable) → normalizer.pre_validate() regex fallback
  │   not ok → FAIL
  ▼
compiler_client.compile_xml()           (Node subprocess: compile-pom.js)
  │   writes input.xml, runs:
  │     1. fit-grow.fitGrow(xml)          unless POM_FIT_GROW=0 or "<!-- fit-grow: off -->"
  │          (writes fitted.xml alongside, if it changed anything)
  │     2. buildPptx(fitted-or-original)  (retries on the ORIGINAL xml if the fitted one
  │                                        itself fails to build — a fit-grow bug must
  │                                        never cost a retry)
  │     3. postProcessPptx(buffer)        table-cell vertical centring (pptx-post.js);
  │                                        failure here is non-fatal (PPTX_POST_SKIPPED warning,
  │                                        ships POM's own unprocessed .pptx)
  │     4. geometry.js dump               unless POM_GEOMETRY=0; non-fatal (GEOMETRY_SKIPPED)
  │   writes compile-result.json + presentation.pptx + geometry.json
  ▼
layout_audit.audit_layout(cleaned_xml)        (mechanical XML checks, always)
  │
  ▼ (only if compile_result.ok)
geometry_audit.audit_run_folder(output_dir)   (compares geometry.json vs the .pptx's drawn shapes)
  │
  ▼
validator_node returns {normalize_result, validate_result, compile_result, layout_issues}
```

### 5.2 `compiler/normalizer.py` — `normalize_xml()` (line 683) deterministic fix codes
Every fix is reproduced against a verified POM 10.3.0 behaviour (per the file's own header comments) and emits an `{code, message, auto_fixed}` issue. In application order: `ILLEGAL_CHARS_REMOVED` (NUL/control chars) → `MARKDOWN_FENCE` (stray ``` fences) → **"early" structure fixes** (`_fix_structure(..., "early")`, 576): `AMPERSAND_ESCAPED` (bare `&`), `ATTR_MARKUP_STRIPPED` (markup tags written inside an attribute value, e.g. `title="<B>...</B>"`), `ATTR_CONFLICT_FIXED` (a bare `shadow="..."` beside its dotted form, which POM parse-errors on), `BORDER_SHORTHAND_EXPANDED` (CSS `border.width="t r b l"` → per-side `border<Side>.width/color`), `MARK_TO_SPAN` (a `<Mark>` highlighter becomes `<Span color>` unless its colour is a light `*Soft` token, in which case it's kept as a real highlighter — `_mark_to_span`/`_readable_text_color` compute a contrast-safe ink from the marker's hue via HLS lightness stepping), `HIGHLIGHT_REMOVED` (`highlight=` attribute dropped), `ITEM_BORDER_REMOVED` (border attributes stripped from `Td`/`Li`/`Col`/`FlowNode`/`TimelineItem`/`ProcessArrowStep`/`PyramidLevel`/`MatrixItem` — verified-rejected by POM) → `HASH_COLOR` (leading `#` stripped) → `ALPHA_COLOR_BLENDED` (8-digit RRGGBBAA blended onto white, `_blend_alpha`) → `SPACING_TO_GAP` → `FONTWEIGHT_TO_BOLD` → `SHAPE_TYPE_ALIAS` (circle/oval/square/rectangle/roundedrect → POM's actual `shapeType` names) → `BORDER_ACCENT_FIX` → `ZERO_SPACING` (removed, never "0") → `ZERO_STROKE_REMOVED` (a zero-width border/line/outline fails buildPptx — the whole stroke group is dropped, not just the width) → `ZERO_DIM` (reported, **not** auto-fixed — `w`/`h`/`minH`/`fontSize` ≤ 0 needs regeneration) → `TEXT_CONTAINER_FLATTENED` (`content_model.flatten_text_containers` — a `<Td>`/`<Li>` body containing only `_FLATTEN_SAFE` layout nodes, e.g. an HStack of Icon+Text, collapses to its plain-text content) → **"late" structure fixes** (620): `EMPTY_CELL_FILLED`, `EMPTY_TEXT_REMOVED`, `EMPTY_ITEM_REMOVED`, `TABLE_COLS_PADDED` (a row with more cells, colspan-counted, than declared `<Col>`s gets extra width-less `<Col/>`s), `TABLE_NUMERIC_COLS_SHARED` (a numeric column's pixel width is dropped so it shares space equally), `CHART_FOCUS_LATEST` (a one-series time-period bar/column chart's accent focus colour is moved to the *latest* period, unless the slide text names a different one), `CONTROL_CHAR_REMOVED`, `TEXT_WHITESPACE_TRIMMED` → `ICON_NAME_NORMALIZED`/`UNKNOWN_ICON_REMOVED` (`compiler/icons.py`) → `FONT_FLOOR` (any `fontSize < 14` raised to 14) → Pyramid-specific fixes (`PYRAMID_FONTSIZE_FIX`, `PYRAMID_TEXTCOLOR_FIX` — contrast-aware) → `find_violations()` → `INVALID_CHILD` (content-model violations, reported not fixed — blocks before parseXml, §2.9) → speaker-notes extraction (`<Notes>` stripped out) → theme stripped → **the growth-fallback passes** (`compiler/grow_fallback.py`, §5.3): `KPI_ROWS` (`compiler/kpi_grid.py`), `GROW_BAND_ADDED`, `TEXT_BOX_UNSQUEEZED`, `GROW_ROWS_ADDED`, `GROW_LONE_CARD`.

### 5.3 `compiler/grow_fallback.py` and `compiler/kpi_grid.py` — Python-side layout fallbacks (pre-fit-grow)
These are text-editing passes over the raw XML string (regex tag-walker `_TAG_RE`/`_elements()`), run inside `normalize_xml()` **before** the slide ever reaches the Node fit-grow pass:
- `ensure_growing_band()` (`grow_fallback.py:77`) — if the root `VStack`'s direct children (bands) have no `grow`/`h` at all, gives `grow="1"` to one band (preferring a chart/diagram band, else the band with the most nested nodes), skipped entirely if any band contains a `Table` (tables fill via fit-grow's own row-growth instead).
- `share_row_height()` (130) — if a growing `VStack`'s children are all non-flexible `HStack` rows, gives each row `grow="1"` so they share the parent's grown height.
- `fill_lone_child()` (159) — if a growing band's *only* child is a single non-flexible card (has a background or contains a fill-type diagram), that card gets `grow="1"`.
- `unsqueeze_text_boxes()` (199) — a long (`≥60` char) text box with `w="max"` sitting beside KPI-tile/card siblings in an `HStack` gets `grow="1"` instead of `w="max"`, because POM gives `w="max"` an *auto* flex-basis (its own one-line width) which can squeeze neighbouring tiles to nothing; `grow` gives it a zero basis so it shares spare width instead.
- `kpi_grid.kpi_rows()` (`kpi_grid.py:50`, uses `lxml`) — if a slide's entire body (below header texts, above a trailing caption) is one `HStack` of 4–6 "stat tile" cards (a card with a ≥24px bold number ≤14 chars), it's rewritten into 2 rows of equal-width tiles (`_WIDTH = {2: "49%", 3: "32%"}`) — because 4+ tiles in one 1280px row are width-bound (~230-290px, numbers can't grow past ~50px) while 2-3 per row let numbers grow toward ~96px.

### 5.4 `compiler/nodes/element_refs.py` — KPI element refs (`POM_BLOCKS=kpi`, default)
`mode()`/`refs_on()` (72-81) read `POM_BLOCKS` (default `"kpi"`; `"off"` disables this whole mechanism; `"tiles"` also uses it as the final fill step). Contract: the generator writes ordinary POM nodes to compose the tile's container/icon/fills, but places each KPI item's text with self-closing `<Text ref="<component_id>.<item-index>.<label|value|note>"/>`. `fill_refs()` (140) is the code half: walks every `ref`-bearing element, validates it against the plan (`NODE_REF_UNKNOWN`/`NODE_REF_DUPLICATE`/`NODE_ITEM_MISSING`/`NODE_FIELD_MISSING`/`NODE_BYPASSED`/`NODE_ATTR_IGNORED`/`NODE_FOCUS_UNNAMED`/`NODE_VALUE_TEXT`, severities in `SEVERITY`, 35), and **writes the literal text itself** — the LLM never gets to see or type the actual KPI numbers (enforced upstream in `generator.py`, §2.8). Code also owns: per-component uniform value font size (`growStats`-compatible ids `kpi{v|h}<rank>-<cid>-<i>`, rank = plan weight 0=hero..3=minor, so fit-grow never grows a lower-priority component's numbers past a higher-priority one), the unit-span split (`value_parts.split_value`/`unit_px`/`unit_share`), colour defaults from `kpi_tones`/role tokens with dark-fill-aware remapping (`READS_ON`/`ON_FILL`), square corners on KPI tiles (`borderRadius` stripped), and spare-width distribution across a content-sized tile row (`_fill_rows`). `_unwrap_refs()` (279) specifically fixes the LLM wrapping a ref `<Text>` inside another styled `<Text>` (POM rejects nested Text; the repairer used to then flatten the slide and duplicate labels) by hoisting the ref tag into the wrapper's place. `prompt_line()` (356) is the per-component line injected into the generator user prompt in place of the component's real `content_data` (lengths, field names, tone/icon/focus metadata — never values).

### 5.5 `compiler/nodes/tiles.py` / `cards.py` — tile/card node expansion (`POM_BLOCKS=tiles`, opt-in)
A further layer on top of §5.4: the LLM writes `<KpiGrid ref="cid" variant="..." .../>` / `<Kpi ref="cid.i" .../>` (and `<CardGrid>`/`<Card>` for `card_grid` components) as **group/item tags**, resolved against `knowledge/core/block-variants.yaml`'s `tile_nodes.kpi`/`tile_nodes.card` blocks. `tiles.expand()`/`cards.expand()` build the actual tile/card subtree in code — four-layer attribute resolution (`house_look` → group-variant look → group's own attributes → item-variant look (or an item's own variant replaces the whole chain) → item's own attributes), with role colouring resolved from an explicit `color=` ask, else the plan's `kpi_tones`/card `tone` (`tone_of`/`role_value`), and the plan's singled-out item (`emphasis_index`/`focus_index`) driving `inverted`/`size="hero"` — **the LLM never chooses which item is the focus**. `tiles.fill()` (497) is the composed entry point used by `validator.py`: `cards.expand → tiles.expand → element_refs.fill_refs`, so under `POM_BLOCKS=tiles` a slide passes through three expansion/fill stages before `normalize_xml`. Card-specific logic in `cards.py` additionally measures real text length to choose grid column counts (`columns()`, capped at 4/3/2 by text density), splits a step's body into bullet points on sentence/semicolon boundaries (`points()`), and computes width shares for an uneven "steps" row by `sqrt`-scaling each card's text length (`_step_shares`). A `card_grid` whose `card_layout == "matrix"` is explicitly **deferred** — `card_components()` excludes it, so it still goes through the old hand-drawn recipe/visual-intent path even under `POM_BLOCKS=tiles`.

### 5.6 `compiler/palette_tokens.py` — derived colour roles
`derive_tokens()` (91) computes, from a palette's ~10 authored colours: `{role}Soft` (a pale mix toward `surfaceAlt`, `SOFT_MIX_LIGHT=0.13`/`SOFT_MIX_DARK=0.22`) and `{role}Text` (same hue, HLS lightness stepped via `_step_lightness()` until it reads ≥4.5:1 against `surface`/`surfaceAlt`/its own Soft) for each of `accent`/`positive`/`negative`/`warning`; `onAccent` (white, else the palette's own ink, else whichever of a candidate set reads best on `accent`); `border` (lightness-stepped to ≥1.4:1, since a literal authored border could be near-invisible — the specific bug this guards against, corporate-slate's `E2E8F0` at 1.17:1, is named in the code comment); `neutral` (authored, else a grey mix); `panelDark`/`onPanelDark` (a fill that is dark on *every* palette — light palettes use `textMain`, dark palettes use the accent hue pulled to `PANEL_DARK_L=0.2` lightness so the "inverted focus panel" reads apart from the slide by hue, not just lightness). All lightness changes happen in HLS space (hue/saturation preserved) specifically to avoid "mixing toward ink turns saturated orange into brown."

### 5.7 Supporting compiler modules
- **`compiler_client.py`** — the only Python↔Node bridge; `compile_xml()`/`validate_xml()` shell out to `src/node/compile-pom.js` via `subprocess.run` (120s / 30s timeouts respectively; `NODE_BIN` env overrides the `node` executable), reading only `compile-result.json`, never parsing stderr. `deck_font()` (60) injects `fontFamily="Inter"` (env `POM_DECK_FONT`, `"none"` disables) onto every text-bearing tag lacking one, before writing `input.xml` — this is distinct from, and upstream of, `font_embed.py`'s job of actually embedding the font bytes into the final `.pptx`.
- **`content_model.py`** — `find_violations()` / `flatten_text_containers()` / `nesting_compile_failure()`, all built from `nodes.yaml`'s `children` field (§4.1); the one place parent/child legality is computed.
- **`geometry_audit.py`** — compares `geometry.json` (POM's own positioned-box tree, from `src/node/geometry.js`) against what is actually drawn inside the compiled `.pptx` (`_drawn()`, reading the slide XML's `sp`/`graphicFrame`/`pic`/`cxnSp` shapes, with table-row-sum and text-need estimation). Emits `GEOM_SPILL`/`GEOM_COLLISION`/`GEOM_OFF_SLIDE`/`GEOM_TEXT_OVERFLOW`/`GEOM_CARD_EMPTY`/`GEOM_BOX_EMPTY`/`GEOM_SLIDE_SPARSE`/`PLACEHOLDER_TEXT`, each tiered `error` (>10px, triggers repair) / `warning` (4-10px borderline, passed to the visual critic to confirm on the screenshot) / `info` (fill-only, code-owned, never repaired).
- **`layout_audit.py`** — pure-XML mechanical checks (root size/alignment, font floor, zero dims, missing diagram dims, `w="max"` misuse on a VStack child, nesting depth, table column-width sums, root-VStack/HStack band-height-sum overflow estimation, table-too-wide-for-its-card, `LOW_CONTRAST` via real WCAG contrast math resolved through the slide's own `<Theme>` tokens, `LITERAL_COLOR` hex-instead-of-token detection). `REPORT_ONLY_CODES` (367) is the set that is scored/bundled but **never shown to the critic** — `LOW_CONTRAST`, `LITERAL_COLOR`, every `GEOM_*` code, `PLACEHOLDER_TEXT` — except that `critic.critic_layout_issues()` (critic.py:61) re-admits any `GEOM_*` issue specifically tiered `warning` back into what the visual critic sees, so it can confirm borderline cases against the actual screenshot.
- **`repair_guidance.py`** — `build_error_guidance()` (targeted fix text per diagnostic code), `error_signatures()`/`is_stalled()` (the repair-loop stall detector, §2.10), `needs_regeneration()` (structural-error detector forcing REGENERATE), `select_repair_knowledge()` (loads only the `knowledge/components/<Node>.yaml` slices for nodes named in the actual errors — so the repair prompt never re-sends the whole generation contract).
- **`value_parts.py`** — `split_value()`/`unit_share()`/`is_sentence()`, the one KPI-value-string parser shared by `element_refs.py`, the composer script, and plan checks' `KPI_VALUE_TEXT` detector.
- **`node_facts.py`** — the verified-facts/probe-test infrastructure described in §4.2; also hosts `open_choice_violations()`/`flow_link_violations()`, lint checks run by tests over the prompt/knowledge text itself (catching an example that silently fixes an "open choice" attribute instead of showing all its legal values, or a `FlowConnection` that skips/reverses a node).
- **`icons.py`** — `valid_icon_names()` (from `icon-names.txt`), `canonical_icon_name()` (camelCase/snake_case → kebab-case), `fix_icon_names()` (rename-if-known-alias, else strip the `<Icon>` entirely — no fuzzy matching, since a near-miss guess draws the *wrong* symbol).
- **`font_embed.py`** — subset-embeds Inter/JetBrains Mono (from `src/node/fonts/`) into the **final** assembled `.pptx` only (called once by `deck_assembler_node`/`evaluator_node`, never per-slide), building a real Embedded-OpenType part per face actually used in the deck's runs, respecting the font's own `fsType` embedding-restriction bit.
- **`pptx_merge.py`** — the ZIP-level multi-slide stitcher used only as `deck_assembler`'s fallback when the re-combined-XML compile fails; copies chart/embedding parts with renumbered IDs so each slide's chart data survives the merge.
- **`screenshot.py`** — Windows-only PowerPoint COM automation (`comtypes`) for both the critic's per-slide screenshots and the evaluator's final-deck screenshots; tracks and force-kills only `POWERPNT.EXE` PIDs that appeared *during* its own call (never a PID that existed before), to avoid poisoning a user's already-open PowerPoint or leaving zombie processes that corrupt the next render.

### 5.8 The inactive "node contract" route (`src/compiler/nodes/{validate,native,prompt_lines,spec}.py`)
Confirmed by grep: `prompt_lines.render_prompts()`, `native.fill()`, and `validate.check_skeleton()` are referenced only from `scripts/node_test.py` and `scripts/phase0b/expand.py` (the "1a" slot-test tooling described in AGENTS.md's roadmap) — **not** from `src/agents/generator.py` or `src/agents/validator.py`. `generator.py`'s own `_render_prompts()` is an unrelated same-named local function. This means: the `<KpiRow ref>`/`<CardGrid ref>`/`<Callout ref>`/`<SlideHeader ref>` **derived-tag** vocabulary and the native-tag-with-children-filled-by-code vocabulary (`spec.py`'s `block_for`/`tags_for`/`variants`/`NATIVE_ATTRS`, `native.py`'s per-kind fillers for `Text`/`Ul`/`Table`/`Chart`/`Timeline`/`ProcessArrow`/`Flow`/`Pyramid`/`Tree`/`Matrix`) exist, are unit-tested in isolation, and are exercised by the standalone node-test/gallery scripts, but a live pipeline run through `src/graph.py` never reaches them. Only the KPI/card **tile**-node system (`element_refs.py`/`tiles.py`/`cards.py`, §5.4-5.5, a sibling but materially different design built later) is live, gated by `POM_BLOCKS`.

## 8. Ambiguities, latent bugs and TODOs flagged during this review

These were found by reading the code, not by running it — flagged here rather than smoothed over, per the user's standing instruction.

### 8.1 `agents/critic_schema.py` — possible `NameError` building `VisualCriticOutput`'s schema
`critic_schema.py` has `from __future__ import annotations` (line 7) and imports only `BaseModel`, `Field`, and two `*Literal` type aliases from `src.state` (lines 9-12) — it never imports `typing.Literal` itself. Yet `VisualCriticOutput` (line 63) declares two fields with a **bare** `Literal[...]` annotation:
```python
overall_assessment: Literal["layout_broken", "needs_tuning", "good"] = Field(...)   # line 69
repair_strategy: Literal["patch", "regenerate", "none"] = Field(...)                # line 74
```
Because of PEP 563, these annotations are stored as strings and only evaluated when Pydantic builds the model's schema, using `critic_schema`'s own module globals — which do not contain the name `Literal`. If Pydantic resolves this eagerly (at class-definition / import time) the module import itself would fail; if it defers resolution to first schema use, the failure would surface inside `visual_critic.run_visual_critic()`'s `llm.with_structured_output(VisualCriticOutput, ...)` call (`visual_critic.py:105`) or the subsequent `.invoke()` — and **both** of those sites are reachable only from inside broad `except Exception` handlers (`run_visual_critic`'s own try/except around `.invoke()`, and `critic_node`'s outer try/except which fails open to `passed=True, issues=[]`). I did not execute the code to confirm which of these happens, so I can't say definitively whether this has ever actually fired in a real run (if `with_structured_output` resolves schemas lazily per-call rather than at bind time, or if some other import path happens to pull `Literal` into that module's namespace via a side effect I didn't trace, it may be silently fine). What is certain from static reading: **the import is missing**, and if the error does fire, the design of the surrounding error handling is such that it would be swallowed as "no visual issues found" rather than surfaced — worth a deliberate test (`from typing import Literal` added, or a quick `VisualCriticOutput.model_json_schema()` smoke-test) rather than leaving it to chance. Note also that the sibling class `CriticOutput` in the same file (line 33) is defined but **never referenced anywhere else in `src/`** (confirmed by grep) — it appears to be dead code, possibly a leftover from an earlier non-visual critic design.

### 8.2 `agents/slide_replanner.py:85` — unpacked return value from `plan_single_slide`
`slide_component_planner.plan_single_slide()` is documented and implemented to return a 2-tuple `(SlidePlan, usage_dict)` (`slide_component_planner.py:222`, `return plan, usage`). In `slide_replanner.resolve_slide_plan()`:
```python
updated_plan = plan_single_slide(
    outline_slide,
    outline_plan=outline_plan,
    deck_settings={"theme": theme_info.get("name", "")},
)
```
this is **not** unpacked — `updated_plan` is bound to the whole `(SlidePlan, usage)` tuple. The next line, `updated_plan["slide_index"] = slide_plan.get("slide_index", 0)`, would raise `TypeError: 'tuple' object does not support item assignment` on any call that reaches this branch. This code path (`resolve_slide_plan`) is only invoked from `api.py`'s `edit_slide /runs/{id}/slides/{i}/edit` endpoint, and only when the user's NL feedback introduces a component kind the existing plan doesn't have (`needs_replan` true, line 74) — a comparatively rare edit. `api.py`'s call site already wraps `resolve_slide_plan()` in a try/except that falls back to `(slide.slide_plan, {})` on any exception (`api.py:1124-1130`), so the practical effect is: this specific "replan because the edit needs a new component kind" feature silently no-ops to "use the plan unchanged, contract `{}`" rather than crashing visibly. This looks like a straightforward unpacking bug that should be `updated_plan, _usage = plan_single_slide(...)`.

### 8.3 `agents/context_builder.py` — `has_grammar` is always `True`
`build_contract()` hardcodes `has_grammar = True` (line 590) and passes it straight through to `_select_notes(..., has_grammar=True)`. Inside `_select_notes` this permanently suppresses: the `kpi_numeral_note` from `text.yaml`, each component's own `structure:` block, `design-language.yaml`'s `design_principles`/`card_recipe.rules`/`bullet_list_styling`/`chart_sizing` sections (lines 345-354). Given there is no other code path that ever sets it `False`, these knowledge sections are currently **permanently dormant** in the live generation contract — not a bug exactly (the house-style grammar + recipes are presumably meant to supersede them), but worth flagging since `design-language.yaml` still carries this content and a reader of that file would reasonably expect it to reach the prompt.

### 8.4 `api.py:1259` `_do_finalize` — possible tuple/string mismatch with `assemble_deck_xml`
`deck_nodes.assemble_deck_xml()` has the signature `-> tuple[str, int]` and its body (`deck_nodes.py:57-58`) does return `(xml, len(blocks))`; its one in-pipeline caller, `deck_assembler_node`, correctly unpacks it: `combined_xml, assembled_count = assemble_deck_xml(...)` (`deck_nodes.py:188`). But `api.py`'s `finalize_deck` endpoint (`_do_finalize`, line 1248) calls it as:
```python
combined_xml = assemble_deck_xml(
    [s.current_xml for s in sorted(session.slides, key=lambda x: x.slide_index)],
    session.theme_element,
)
if not combined_xml:
    return FinalizeResponse(ok=False, error="No valid slide blocks found")
```
without unpacking — `combined_xml` here is bound to the 2-tuple, which is always truthy (a non-empty tuple), so the `if not combined_xml` empty-check can never fire the way it's apparently meant to, and the subsequent `compile_xml(combined_xml, output_dir)` (line 1259) would receive a `tuple` where a `str` is expected, which should raise inside `compiler_client.compile_xml()` (it calls `.resolve()`/writes `xml` to a file via `Path.write_text`, which does not accept a tuple) — caught by the endpoint's own `except CompilerError` only if that specific exception type is what's raised; a raw `TypeError` from `write_text` would propagate as an unhandled 500. This endpoint (`POST /runs/{run_id}/finalize`, the "reassemble edited slides into a final deck" feature) appears to be exercised only by the slide-editor UI flow, not by the main generation path, so it would not affect a normal `/generate` run — but as written it looks like it would fail on first use.

### 8.5 Design-level ambiguities (not bugs, but worth naming since AGENTS.md's own working notes describe them as open)
- The plan-reviewer **loop** described in AGENTS.md's roadmap notes ("make `plan_reviewer` a real feedback loop... issues tagged by slide and stage → outline issues patch the named outline slides, slide issues re-plan only those slides") is **not implemented** in this codebase snapshot: `route_after_plan_review` (`graph.py:158`) unconditionally routes to `style_resolver` regardless of `confidence_score`/`approved`/`issues`. The review is purely advisory/logged.
- `elicitation_wait` (`graph.py:243`) is a true dead-end node (`return {}`, edge to `END`) with no LangGraph checkpointer visible in `compile_graph()` (`build_graph().compile()`, no `checkpointer=` argument) — resuming after elicitation answers means the API layer must start an **entirely new** `initial_state(..., elicitation_answers=...)` run rather than resuming the same graph execution. This matches what `api.py`'s `/plan/outline` endpoint does (it calls `check_and_elicit` and `outline_planner_node` directly, bypassing the graph's elicitation branch entirely, rather than ever actually hitting `elicitation_wait` in a `/generate` run) — worth confirming this is the intended usage pattern rather than an oversight, since a plain `POST /generate` whose elicitor decides the request is insufficient would currently just end the run at `elicitation_wait` with no `pptx_path` and no obvious signal in the SSE stream beyond the `elicitation_needed` event name.
- `SLIDE_PLANNER_MAX_PARALLEL`/`SLIDE_PLANNER_MAX_CONCURRENCY` (`slide_component_planner.py:48-49`) are read into module constants but I found no semaphore, `asyncio.Semaphore`, or executor configuration anywhere in `slide_component_planner.py` or `graph.py` that actually consumes them to cap concurrency — the real fan-out concurrency is whatever LangGraph's own `Send()` execution model does. These constants may be vestigial from an earlier (pre-`Send()`) manual-threading implementation.
